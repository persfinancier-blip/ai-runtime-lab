# LAB-100 — supported activation authority extension model

Date: 2026-09-04
Issue: #185
Status: contract frozen; exact RED/GREEN pending

## Question

How should LAB-090 accept a provider-side activation/fencing implementation without trusting arbitrary subclass overrides, caller-owned mutable state, inherited identity rotation, or self-asserted lifecycle return strings as proof that a real external fence exists?

## Fresh source evidence

PR #175 currently defines `FencedActivationProvider` as a normal subclass of `SignedAnchorProvider`. `rotate_provider()` and restart recovery accept the activation implementation with `isinstance(provider, FencedActivationProvider)`. The coordinator then treats `prepare_activation()`, `activation_status()`, `commit_activation()`, `release_activation()`, and `abort_activation()` return values as authoritative provider-side lifecycle evidence.

The provider stores a caller-supplied optional `ActivationState` as public `self.activation_state`; `prepare_activation()` allocates fences from mutable `next_fence`; `increment()` blocks only while mutable `pending` is non-null. The parent `SignedAnchorProvider.rotate()` remains independently callable and replaces provider identity/generation/key without activation-aware quiescence checks.

The issue already records three independent failures that exact-type checking alone does not solve:

1. arbitrary subclasses can fabricate valid-looking activation lifecycle responses without installing a real fence;
2. exact `FencedActivationProvider` can strand a pending ticket through inherited identity rotation;
3. exact provider can lose its fence through out-of-band mutation of caller-retained `ActivationState`, and reconstructed state can regress `next_fence` below historical tickets.

## Impossibility boundary

A coordinator cannot prove provider-internal fencing semantics solely from messages generated by an otherwise untrusted provider implementation.

Adding a MAC/signature to `PREPARED`, `COMMITTED_FENCED`, or `RELEASED` only authenticates that the same provider authority emitted those claims. It does not independently prove that its write path really rejects increments while a fence is pending. If arbitrary provider code controls both the claimed status and the authenticated receipt, cryptography cannot convert an unaudited implementation into a trusted fencing primitive.

Therefore LAB-100 must make the provider-side implementation/capability itself an explicit trust root. The coordinator may verify authenticated observations from that capability, but it must not claim those observations prove the semantics of arbitrary extension code.

## Frozen V1 extension model

### 1. Coordinator accepts an `ActivationAuthority`, not arbitrary provider subclasses

The LAB-090 coordinator-facing object is a sealed/registered authority capability with value-only request/results. It exposes only the activation operations needed by LAB-090 and authenticated provider observations needed by LAB-080/081 reconciliation.

No generic object reflection, direct `ActivationState`, raw provider object, inherited `rotate()`, arbitrary subclass hook, or caller-owned mutable state is part of the supported surface.

### 2. Two supported authority classes

**Reference in-process authority**

For executable lab tests, support one exact audited implementation constructed by a factory that creates and exclusively owns its activation state. Its state reference is not supplied by callers and is not exposed as mutable public authority. Identity/generation changes are activation-aware and fail closed unless the state machine is quiescent or is performing the explicit coordinated generation transition.

This is an implementation trust decision, not a proof derived from Python type names. Exact-type admission is acceptable only as the narrow enforcement mechanism for this one audited implementation.

**External/custom provider authority**

Custom providers are not admitted by subclassing the reference class. They require an explicit trusted adapter/capability registration whose provider-side implementation and persistence semantics are independently accepted/audited by deployment policy. Registration returns the coordinator-facing sealed `ActivationAuthority`; the coordinator never receives the raw custom provider object.

Provider implementation identity/version and protocol version are construction-bound metadata in the LAB-094..096 retained-authority graph. Changing them is an authority transition, not ordinary runtime rebinding.

### 3. Authenticated activation protocol

Authority responses are value-only and bind at least:

- provider_id;
- provider generation;
- activation_id;
- expected position;
- monotonic fence token;
- activation lifecycle state;
- operation/request identity;
- protocol version;
- provider implementation/adapter identity;
- challenge/nonce where replay protection is required.

The coordinator verifies these through the already trusted provider verification authority and binds the exact activation-ticket digest into the authenticated provider-generation transition as frozen by LAB-097..099.

These receipts authenticate *which trusted activation authority said what*. They do not by themselves establish the trustworthiness of arbitrary provider code.

### 4. Fencing semantic invariant

For an admitted authority, one provider-owned atomic state machine must govern both activation lifecycle and external write/increment admission.

Required invariant:

`pending activation exists -> ordinary increment/write CAS for that provider generation is impossible`

The same provider-owned durable authority must atomically own:

- current provider identity/generation;
- current anchor position/CAS metadata;
- activation pending/committed state;
- monotonic fence cursor/history necessary to prevent token reuse;
- idempotency/request-result state needed for UNKNOWN reconciliation.

The implementation may use different storage internally, but deployment trust must cover the atomicity relationship. Coordinator SQLite is not the provider-side fence authority.

### 5. Identity rotation

Generic inherited provider identity mutation is unsupported.

A provider identity/generation transition can occur only through the activation-aware authority transition. If any activation is pending or committed-but-fenced, direct identity mutation fails closed. A new authority instance/capability for a new generation is construction-bound only after the coordinated transition and provenance checks complete.

### 6. State reconstruction

Caller-supplied raw activation state is unsupported.

On provider restart, the trusted authority reconstructs from its own durable state and validates before serving operations:

- at most one pending activation for the modeled authority scope;
- committed records are internally coherent;
- `next_fence >= max(all trusted historical/pending/committed fence tokens)`;
- next fresh fence is strictly greater than every prior trusted token;
- provider identity/generation and position metadata match the reconstructed activation state;
- malformed, missing, rollbacked, or ambiguous state fails closed.

The coordinator does not repair a provider's fencing cursor from mutable caller data.

## Composition with retained contracts

- **LAB-090:** owns activation ordering and coordinator recovery; it consumes only the sealed activation authority capability.
- **LAB-093:** lower-trust worker receives only value-only broker façade operations; raw activation authority remains broker-only.
- **LAB-094..096:** retained authority graph binds database identity, bootstrap root, history strategy, plus activation authority implementation/adapter identity and protocol version.
- **LAB-097..099:** authenticated generation transition binds the exact activation ticket digest; initialization and activation provenance are verified before recovery writes.

## RED-first matrix additions

Before production implementation, exact-source execution must prove at least:

1. fake subclass returns PREPARED/COMMITTED_FENCED/RELEASED without installing pending state -> rejected before SQL/history mutation;
2. exact reference authority + direct generic identity rotate while PREPARED -> rejected; pending remains reconcilable;
3. exact reference authority + direct identity rotate while COMMITTED_FENCED -> rejected;
4. caller cannot inject or retain mutable activation state that controls fencing;
5. caller cannot clear/replace pending state out of band;
6. reconstructed fence cursor below historical maximum -> fail closed;
7. duplicate fence token in reconstructed trusted state -> fail closed;
8. fresh token after restart is strictly greater than all historical tokens;
9. arbitrary custom subclass is not accepted as a production extension path;
10. explicitly registered trusted adapter with matching implementation/protocol identity is accepted;
11. adapter implementation/version rebinding without authenticated authority transition -> fail closed;
12. forged/mismatched authenticated activation receipt -> fail closed before SQLite/provider mutation;
13. authenticated receipt from correct authority but wrong activation_id/position/fence/generation -> fail closed;
14. pending activation blocks ordinary increment/write through the same provider-owned atomic state machine;
15. UNKNOWN after provider commit reconciles without releasing the fence before durable coordinator acknowledgement;
16. broker restart reconstructs the same trusted authority identity and validates provider-side state before worker endpoints open;
17. LAB-093 restricted worker cannot reach raw authority/provider state;
18. LAB-097..099 ticket digest mismatch is detected before recovery mutation.

## Decision

`LAB100_SUPPORTED_ACTIVATION_AUTHORITY_MODEL_FROZEN`

The supported extension mechanism is explicit trusted authority registration/adaptation, not inheritance. The reference in-process implementation may be exact/sealed for the lab, but production/custom extensibility crosses an explicit trust-registration boundary. Authenticated lifecycle receipts are required for binding/replay/recovery, yet are not misrepresented as independent proof of arbitrary provider code's internal fencing semantics.

No production code changed in this step because exact repository RED/GREEN execution remains unavailable in the current runtime.
