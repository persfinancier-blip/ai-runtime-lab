# LAB-093 worker-session revocation / broker re-entry protocol V1

Date: 2026-09-04
Status: FROZEN DESIGN / RED-FIRST; production implementation waits for executable branch gates.

## Problem

LAB-093 already establishes that a ledger-only recipient must not be able to recover caller-owned mutable `AttestedCatchup`, provider, verifier/keyring or LAB-090 activation capabilities through the ledger object. The broker startup contract also requires a fresh clean verification/evidence/plan pass before delegation.

That is insufficient once a worker session has already been delegated. A long-lived worker may remain alive while the broker's retained authority graph changes: provider generation rotates, activation authority upgrades, authenticated provenance head advances, a previously aligned external terminal anchor becomes unresolved, or a recovery/startup re-entry begins. Without an explicit revocation boundary, a capability that was valid when issued can become stale while still being callable.

The security property is therefore temporal, not merely structural:

> No worker capability issued under authority/provenance/runtime state S may authorize new work after the broker has observed or initiated a transition away from S; no in-flight work may publish durable/external effects after revocation unless the effect was already durably committed under the exact pre-revocation operation identity and is completed only by broker-owned recovery semantics.

## Scope and composition

This protocol composes with:

- LAB-087: broker/process owns the sole writable handles;
- LAB-090/LAB-100: activation fencing and activation-authority identity/version;
- LAB-091: one-shot write ownership / concurrent writer exclusion;
- LAB-093: least-capability worker façade;
- LAB-097..099: authenticated initialization/generation/activation provenance;
- canonical provenance chain, durable append/recovery, startup verifier/planner, external-evidence collector, recovery executor and broker startup state machine.

It does **not** give workers raw SQLite connections, provider handles, activation handles, mutable verifier/keyrings, recovery executor objects or direct authority-transition APIs.

## 1. Session identity

Every delegated worker session has an immutable broker-issued `WorkerSessionToken` containing only value data:

- `session_id`: 128-bit random or collision-resistant opaque identifier generated by the broker;
- `session_epoch`: broker-local U64 monotonic delegation epoch;
- `provider_generation_id`;
- `activation_authority_digest`;
- `provenance_head_digest`;
- `provenance_head_epoch`;
- `external_terminal_position` and authenticated terminal receipt digest / snapshot binding used by the final delegation gate;
- `capability_profile_digest`: canonical digest of the exact least-capability façade/method set and policy limits;
- optional expiry/deadline only as an additional bound, never as the primary revocation mechanism.

The token is not itself a provider capability and cannot reconstruct one. The broker keeps the authoritative session record privately.

`session_epoch` is independent from provenance epoch. It changes whenever the broker invalidates previously delegated work even if durable provenance has not yet changed (for example, before beginning a provider rotation).

## 2. Capability-generation binding

Every worker request carries:

- `session_id`;
- `session_epoch`;
- broker-issued `request_id` unique within the session;
- method name / operation class permitted by the capability profile;
- immutable request payload digest.

Before accepting **each new operation**, the broker checks that the private current session record is `ACTIVE` and all of these still equal the broker's currently verified authority/runtime state:

1. session epoch;
2. provider generation;
3. activation-authority digest;
4. authenticated provenance head digest+epoch;
5. required external-terminal continuity snapshot class (`ALIGNED` only);
6. no unresolved activation condition;
7. no startup/recovery/re-entry transition in progress.

A worker never self-validates these fields from stale local copies.

## 3. Revocation triggers

The broker must synchronously move the active session set to `REVOKING` **before** it begins or knowingly accepts any transition that can invalidate a delegated session. Mandatory triggers:

- provider-generation rotation or recovery that may change the generation;
- LAB-100 activation-authority transition/version/protocol change;
- any provenance append that changes the authenticated head, unless the delegated API is explicitly designed as a single broker operation whose completion itself owns that append and the session is revoked before any subsequent request;
- transition into LAB-090 PREPARED/COMMITTED_FENCED unresolved activation state;
- external terminal evidence becomes BEHIND/AHEAD/UNKNOWN/stale/unverifiable;
- startup verifier detects corruption, fork, rollback, authority mismatch, stale cached head or any fail-closed condition;
- recovery executor is about to run a write-capable command;
- broker shutdown/restart or loss of sole-writer lease/ownership;
- explicit administrative/runtime revocation.

The important ordering is `revoke gate first -> stop admission -> quiesce -> transition/recovery`, not transition first and revoke afterwards.

## 4. State machine

Per worker session:

`ISSUED -> ACTIVE -> REVOKING -> REVOKED`

Optional terminal states: `EXPIRED`, `FAILED`.

There is no `REVOKED -> ACTIVE` transition. Re-entry always issues a **new** session id and a strictly newer `session_epoch` after a full clean broker startup/re-entry verification gate.

### ACTIVE

New requests may be admitted after per-request session/current-state comparison.

### REVOKING

- immediately reject new request admission;
- mark all not-yet-started queued work cancelled;
- signal cancellable read/compute work to stop;
- forbid any new durable SQLite/provider/activation side effect from worker-originated work;
- wait only for bounded broker-owned quiescing/classification of operations that already crossed a commit boundary.

### REVOKED

All calls using the old session fail closed with `STALE_WORKER_SESSION`. The worker object may remain in memory/process space, but it has no live authorization.

## 5. In-flight operation classification

At revocation, every accepted operation must be in exactly one broker-owned phase:

1. `ADMITTED_NOT_STARTED` — cancel; no effect allowed.
2. `READ_OR_COMPUTE` — cancel or allow computation to finish, but discard result unless a post-compute session check still succeeds. It may never publish an effect after revocation.
3. `EFFECT_NOT_PREPARED` — cancel before any durable/external effect.
4. `DURABLE_PREPARED` — worker path stops. Exact frozen operation identity is handed only to broker-owned recovery/planner/executor semantics; worker cannot retry it.
5. `EXTERNAL_UNKNOWN_OR_COMMITTED_LOCAL_PENDING` — worker path stops. Reconciliation is broker-owned and uses the exact original request id / frozen bytes only.
6. `COMMITTED` — the committed result is historical fact, but no follow-on worker action is authorized. Response delivery may be retried only as an idempotent presentation of the same committed result, not as a new effect.

This classification prevents the common unsafe pattern "let in-flight writes drain while changing authority underneath them".

## 6. Quiescing barrier

A broker transition that changes provider generation, activation authority or retained provenance authority must not begin its mutating phase until:

- admission is closed for all sessions bound to the old state;
- all queued operations are cancelled;
- every in-flight operation is classified into one of the six phases above;
- no worker-owned code can issue provider/SQLite/activation mutations;
- unresolved prepared/unknown operations have been transferred to broker-owned recovery state, not left callable by the worker.

The barrier is about ownership transfer, not necessarily waiting for arbitrary compute threads to terminate. A compute task may physically continue, but its stale completion token cannot pass the broker's post-compute authorization check.

## 7. Broker re-entry ordering

After any revocation-triggering transition/recovery, delegation can reopen only via:

1. complete/reconcile any exact broker-owned PREPARED/UNKNOWN operation as permitted by the frozen recovery grammar;
2. side-effect-free full startup verifier;
3. fresh authenticated external-evidence collection;
4. pure recovery planning;
5. require `RecoveryPlan.NONE`;
6. require aligned terminal anchor and no unresolved activation condition;
7. construct the new retained authority/runtime snapshot;
8. increment broker `session_epoch`;
9. issue a new session id/token and a new least-capability façade;
10. only then admit worker requests.

No old session/token/façade object is upgraded in place.

## 8. TOCTOU rule for worker results

A worker may perform unprivileged compute against immutable inputs, but before the broker accepts a result that could affect durable state it must re-check the exact session/current authority binding.

If `provenance_head_digest`, provider generation, activation authority, session epoch or terminal continuity changed while the compute was running, the result is stale. It can be recomputed under a new session but cannot be committed under the old authorization.

This rule applies even when the compute output itself is deterministic.

## 9. Handle confinement

A worker façade may contain only methods that marshal requests to the broker. It must not contain aliases/references that expose:

- `sqlite3.Connection` / cursor;
- ledger private mutable handles;
- raw `AttestedCatchup`;
- `.provider` or provider state;
- verifier/keyring mutable objects;
- LAB-090 activation capability/state;
- recovery executor/planner mutation surfaces;
- provider-rotation or authority-upgrade methods.

Revocation is implemented in the broker authorization table/session epoch, not by relying on Python object destruction or worker cooperation. Therefore a copied/stashed façade becomes inert when its session record is revoked.

## 10. Crash/restart

Worker sessions are **not restart-resumable capabilities**. Broker restart invalidates all pre-crash sessions unconditionally.

Durable PREPARED/UNKNOWN operations survive only through the existing broker-owned provenance/LAB-080 recovery records and exact request identities. The worker session that initiated them does not survive and is not needed to reconcile them.

After restart, full startup/recovery verification must finish before any new session is issued.

## 11. Multi-worker semantics

Multiple workers may have concurrent read/compute sessions only if they share the same verified authority snapshot and least-capability policy permits it. Any revocation trigger invalidates **all** sessions bound to the affected snapshot before mutation begins.

Write-capable operations remain serialized through LAB-087/LAB-091 broker ownership. A worker's request id is not authority to bypass this serialization.

## 12. Fail-closed / liveness taxonomy

Retryable by a **new broker cycle**, not within a stale worker session:

- transient external evidence unavailable;
- UNKNOWN exact request requiring reconciliation;
- concurrent legitimate progress that made a plan/session stale.

Fatal until operator/code/state repair:

- authenticated provenance fork/rollback;
- authority digest mismatch without valid transition;
- impossible provider-generation continuity;
- forged/rebound session token or request id;
- stale session attempting an effect after revocation;
- raw mutable handle leakage into worker surface.

## 13. RED-first matrix

Minimum executable regression matrix before production implementation:

1. old session can read before revocation;
2. provider rotation marks old session REVOKING before provider mutation;
3. new request rejected once REVOKING starts;
4. old façade copied before revocation is inert afterwards;
5. old session cannot write after provider-generation change;
6. same generation id but different authority digest invalidates session;
7. activation-authority version change invalidates session;
8. provenance-head advancement invalidates prior session for new operations;
9. terminal anchor becomes UNKNOWN -> admission closes;
10. unresolved activation PREPARED -> admission closes;
11. queued operation cancelled on revocation;
12. running compute may finish physically but result is discarded after epoch change;
13. TOCTOU head change between compute and commit rejects commit;
14. ADMITTED_NOT_STARTED has no side effect;
15. EFFECT_NOT_PREPARED has no side effect;
16. DURABLE_PREPARED is transferred to broker recovery only;
17. worker cannot retry PREPARED request itself;
18. UNKNOWN exact request keeps original request id;
19. worker cannot invent probe/retry request id;
20. COMMITTED result can be re-presented without new effect;
21. revocation does not release/abort LAB-090 fence generically;
22. transition waits for quiescing classification before mutating authority;
23. arbitrary long compute cannot block authority transition once its publish authorization is revoked;
24. restart invalidates all pre-restart sessions;
25. restart can still reconcile durable PREPARED without old worker session;
26. re-entry requires fresh full verify;
27. re-entry requires fresh external evidence;
28. re-entry requires fresh NONE plan;
29. re-entry refuses unresolved activation condition;
30. new session id differs from old;
31. new session epoch strictly increases;
32. old session object cannot be upgraded in place;
33. two workers on same snapshot both revoked by rotation;
34. session from snapshot A cannot call broker after snapshot B installed;
35. capability profile digest mismatch rejects call;
36. unknown/forbidden method rejects before effect;
37. request payload digest mismatch rejects before effect;
38. duplicate committed request id is idempotent presentation only;
39. duplicate noncommitted request cannot become a second effect;
40. worker façade exposes no SQLite connection/cursor;
41. worker façade exposes no AttestedCatchup/provider alias;
42. worker façade exposes no mutable verifier/keyring alias;
43. worker façade exposes no activation capability/state;
44. worker façade exposes no recovery-executor mutation surface;
45. broker losing sole-writer ownership revokes sessions before further writes;
46. stale evidence snapshot cannot authorize a session;
47. forged higher session_epoch is rejected;
48. reused session_id with altered bindings is rejected;
49. epoch exhaustion fails closed before issuing another session;
50. final audit proves no worker-originated durable/provider mutation path bypasses broker per-request binding check.

## 14. Decision

Freeze the protocol as:

`WORKER_SESSION_REVOCATION_REENTRY_V1_FROZEN`.

The implementation order when executable RED/GREEN becomes available is:

1. least-capability façade / private authority handles (LAB-093 baseline);
2. broker session registry + epoch and value-only token;
3. per-request current-state binding check;
4. revocation trigger integration before provider/authority/provenance mutations;
5. in-flight classification + broker ownership transfer for PREPARED/UNKNOWN;
6. restart invalidation;
7. full re-entry gate and regression matrix.

Do not implement this by relying only on timeouts, process killing, garbage collection, token expiry, or mutable `revoked=True` objects supplied to workers. Authorization must be broker-owned and checked at effect boundaries.
